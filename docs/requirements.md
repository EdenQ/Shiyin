# 拾音 Shiyin 3.0：需求規格

> 狀態：已確認（2026-10-15，第三版；使用者以「全部做好再找我」授權開工）
> 第二版（只有自己用、依賴 Python）的規格用 `git show b621ed6:docs/archive/v2/requirements.md` 看。驗收結果裡的任務編號（T-…）的紀錄用 `git show b621ed6:docs/tasks.md` 看，選型實驗用 `git show b621ed6:docs/spikes/<檔名>` 看。
> 本文件定義「要做什麼」。怎麼做寫在 `design.md`，實作順序寫在 `tasks.md`。

## 1. 為什麼有第三版

第二版能用，但只能在開發者自己的電腦上跑：要先裝 Homebrew、Python、ffmpeg，也缺少會議紀錄 app 該有的核心功能。第三版回到最根本的目標重新規劃：

> **做一個完整、可以發布給別人用的 macOS 原生會議紀錄 app。**

技術不沿用第二版的選擇，改依實驗數據決定（design D1）。

## 2. 使用者與發布方式（2026-10-15 已確認）

- 使用者：公司同事和身邊的人，不一定是工程師，也不一定裝了開發工具。
- 發布方式：自己發布 DMG，不上 Mac App Store。原因是 app 要執行 claude、codex CLI，App Store 的沙盒不允許。
- 沒有 Apple Developer 帳號，所以不做公證。使用者第一次打開時要手動放行一次，安裝說明要教怎麼操作。
- 有些人沒有裝 claude 或 codex，要提供 Anthropic、OpenAI API key 的選項。

## 3. 範圍

### 3.0 必須做

- 錄音：麥克風，加上線上會議的系統聲音
- 即時逐字稿、錄音中做筆記
- 正式轉錄（Breeze ASR 25）、說話者辨識
- AI 會議紀錄：範本、待確認、手動編輯、每一條都能跳到錄音
- 匯入與匯出：錄音、逐字稿、會議紀錄、整場會議的封包
- 全文搜尋、倍速播放
- 首次使用引導、DMG 發布、從第二版遷移
- 資料夾、全域快捷鍵、app 內更新（原本列為 P1。使用者要求「全部做好」，2026-10-15 納入 3.0）

### 之後再做（3.1 以後）

行事曆整合（自動帶入會議名稱和與會者）、對會議提問、iPhone 版、多人即時協作、雲端同步。英文版排在 3.1（見第 9 節）。

### 不做

上 Mac App Store、支援 Intel Mac 或 macOS 26 以前的版本、把錄音上傳到任何雲端。

## 4. 資料與隱私原則

| 項目 | 原則 |
|---|---|
| 錄音檔 | 只存在本機，不會上傳。要匯出或分享都由使用者自己操作 |
| 轉錄（即時、正式） | 在本機完成，不連網 |
| 整理成會議紀錄 | 把逐字稿文字、使用者的筆記、詞彙表、會議基本資料，送到使用者選的服務（Claude、Codex、Anthropic API、OpenAI API、Gemini API、OpenAI 相容 API）。選「不整理」就完全離線；OpenAI 相容 API 填本機的網址（Ollama、LM Studio）時，內容也不會離開電腦 |
| 對會議提問、猜說話者（3.5） | 跟整理一樣，把逐字稿、會議紀錄、問題送到使用者選的整理工具；跨會議提問只送找到的相關會議片段 |
| 聲紋（3.5） | 說話者的聲音特徵只存在本機的資料庫，不上傳、不放進匯出的封包；設定裡可以查看、刪除、關閉 |
| API key | 存在 macOS 鑰匙圈，不寫進檔案或 log |
| 使用數據 | 不收集，也不回傳任何統計。「回報問題」只打開瀏覽器的 GitHub 頁面，使用者看過內容、自己按送出；不含會議內容 |
| 資料位置 | `~/Library/Application Support/Shiyin`，權限 700 |

## 5. 功能需求

驗收條件的格式是「當…，系統應…」。優先級：**P0** 是 3.0 一定要有；**P1** 是 3.0 盡量做到，來不及可以延到 3.1。

### R1 錄音（P0）

- R1.1 系統應可以錄麥克風，並讓使用者選擇輸入裝置。
- R1.2 系統應可以錄電腦播放的聲音，例如 Zoom、Google Meet、Teams、瀏覽器裡的線上會議。來源可以選「麥克風」「系統聲音」「兩者都錄」。
- R1.3 錄音中應可以暫停和繼續。
- R1.4 錄音中應顯示經過時間，以及每個來源各自的音量。
- R1.5 當 app 當掉或電腦突然關機時，最多只能遺失最後幾秒的錄音，下次開啟時要自動復原。
- R1.6 應可以連續錄音至少 4 小時。
- R1.7 關掉主視窗後錄音應繼續進行；從選單列可以看到錄音狀態，也可以暫停、停止。
- R1.8 第一次錄音時，應依序說明用途並請求麥克風和系統聲音權限。使用者拒絕的話，要說明到哪裡打開。
- R1.9 錄音中和轉錄中，系統不應進入閒置睡眠。

### R2 即時逐字稿與錄音中筆記（P0）

- R2.1 錄音中應即時顯示逐字稿：一講話就出現暫定文字，定稿延遲在 5 秒以內。
- R2.2 錄音中可以往回捲動看前面的內容；使用者正在往回看時，新文字進來也不要把畫面拉走。
- R2.3 錄音中可以自己打筆記，每一行都會記下當下的錄音時間。整理時 AI 會參考這些筆記。
- R2.4 錄音中可以按一個鍵標記「重點」。標記會顯示在時間軸上，整理時也會被當作重點。
- R2.5 即時逐字稿只是預覽。錄音結束後，改用正式轉錄的結果（R4）。

### R3 匯入（P0）

- R3.1 應可以匯入 macOS 讀得到的音訊和影片檔，至少包含 m4a、mp3、wav、aac、flac、caf、aiff、mp4、mov。匯入方式有四種：拖進視窗、⌘O、拖到 Dock 圖示、Finder 的「打開方式」。
- R3.2 會議日期預設從檔名推算（沿用第二版的規則），推算不出來就用檔案的修改日期。
- R3.3 應可以匯入整場會議的封包（.shiyin，見 R7.4），完整還原錄音、逐字稿、會議紀錄和筆記。
- R3.4 應可以匯入逐字稿檔（srt、vtt、txt），可以單獨匯入，也可以跟錄音一起。只有逐字稿時不用轉錄，直接整理。
- R3.5 應可以匯入 Markdown 檔，當成這場會議的使用者筆記。

### R4 正式轉錄（P0）

- R4.1 錄音結束或匯入後，系統應在本機用 Breeze ASR 25 轉錄，並把詞彙表帶進去當提示。設定裡可以改用 macOS 內建的語音辨識：不用下載模型、速度快很多，但不吃詞彙表（2026-10-15 依真人會議的實測加入，見 D11）。
- R4.2 轉錄中應顯示進度和預估剩餘時間，並且可以取消、重試；app 中途被關掉的話，下次開啟時自動重跑。
- R4.3 一次只轉錄一場，其他場排隊等待。
- R4.4 辨識信心低的段落要標示出來。
- R4.5 使用者不需要安裝 Python、Homebrew 或 ffmpeg。

### R5 說話者辨識（P0，要先通過實驗）

- R5.1 正式轉錄時，系統應分出不同的說話者，逐字稿每一段都標上「說話者 1」「說話者 2」等標籤。
- R5.2 使用者可以幫說話者改名。改名後，整場的逐字稿和會議紀錄都改用新名字。
- R5.3 整理時，AI 要知道每段話是誰說的；待辦的負責人優先使用說話者的名字。
- R5.4 如果實驗結果準確度太差（判斷標準寫在 tasks.md），可以把這項延到 3.1，但要先跟使用者確認。

### R6 會議紀錄（P0）

- R6.1 整理工具可以選 Claude（claude CLI）、Codex（codex CLI）、Anthropic API、OpenAI API，或「不整理」。選 API 的話，要填 API key，也可以選模型。3.4 加上 Gemini API、OpenAI 相容 API，見 R17。
- R6.2 應提供範本：一般會議、一對一、訪談、課堂／演講、腦力激盪。使用者也可以自己新增範本，自訂要哪些段落、每個段落怎麼寫。每場會議可以選範本，換了範本之後可以重新整理。
- R6.3 會議紀錄依範本包含以下內容：標題、摘要、決議、待辦（負責人、期限）、未決問題、依議題分段的詳細內容、自訂段落、待確認。
- R6.4 **每一條紀錄都要附上錄音時間點**，點一下就從錄音的那個位置開始播放（「秒聽紀錄」）。
- R6.5 待確認與校稿沿用第二版：回答題目後，AI 依答案修正紀錄；略過的題目直接移除。
- R6.6 使用者可以直接編輯會議紀錄，包括新增、刪除、修改條目。
- R6.7 每次修改都要留版本，並可以復原。修改包括 AI 整理、校稿、手動編輯、用詞修正。
- R6.8 整理規則沿用第二版：期限要換算成實際日期、負責人只填明確提到的人、推測出來的專有名詞要列進待確認。

### R7 匯出與分享（P0）

- R7.1 錄音可以匯出成 m4a（AAC）或 wav。
- R7.2 逐字稿可以匯出成 txt、srt、vtt、Markdown；docx 是 P1。匯出時可以選擇要不要包含時間點和說話者。
- R7.3 會議紀錄可以匯出成 Markdown、PDF；docx 是 P1。也可以複製成純文字、Markdown 或富文字，直接貼到 Notion、Slack、Word。介面上的名稱是「保留格式」（英文 Formatted），不用「富文字」：一般人看不懂（2026-10-22 使用者要求，Mac、Windows 一起改）。
- R7.4 整場會議可以打包成 .shiyin 檔，內容包含錄音、逐字稿、說話者名字、會議紀錄、筆記和重點標記，用來備份或傳給同事。
- R7.5 匯出的檔案可以用 macOS 的分享選單（Mail、AirDrop、訊息）分享出去。

### R8 播放與逐字稿（P0）

- R8.1 沿用第二版的功能：同步播放、播放中的段落高亮、底部時間軸、點時間點跳播、搜尋、單段編輯、用詞修正（會一起改到會議紀錄，也可以加進詞彙表）。
- R8.2 可以倍速播放：0.75×、1×、1.25×、1.5×、2×。
- R8.3 逐字稿要顯示說話者，也可以篩選成只看某一位說話者的內容。
- R8.4 時間軸上要標出重點標記和待確認題目的位置。

### R9 管理（P0）

- R9.1 全文搜尋：輸入一個關鍵字，同時搜尋所有會議的標題、逐字稿、會議紀錄和筆記，點搜尋結果可以直接跳到那個位置。
- R9.2 資料夾：每場會議可以放進一個資料夾（例如專案名稱、客戶名稱）。側欄可以切換只看某個資料夾；資料夾可以改名、刪除（刪除資料夾不會刪掉會議）。在某個資料夾裡錄音或匯入，新會議就放進那個資料夾。.shiyin 封包會帶著資料夾名稱。
- R9.3 刪除的會議先放進垃圾桶，30 天後才永久刪除；在這之前都可以還原。
- R9.4 儲存空間：轉錄完成後，錄音自動轉成 m4a 以節省空間（可以在設定裡關掉）；設定裡要看得到總共用了多少空間。

### R10 安裝、首次使用、更新（P0）

- R10.1 以 DMG 發布：打開後把 app 拖進「應用程式」資料夾。附上一頁安裝說明，教使用者怎麼放行第一次開啟。
- R10.2 第一次開啟時要有引導，依序完成：介紹 app、請求權限、下載轉錄模型、設定整理工具。
- R10.3 下載模型時要顯示進度，可以暫停和繼續；斷線後可以接著下載；下載完成後要驗證檔案正確。
- R10.4 使用說明沿用第二版的 R14，內容依第三版的功能更新。
- R10.5 從第二版升級時，原本的會議、逐字稿、會議紀錄、詞彙表都要保留。第二版的 Python 環境和舊模型已經用不到，要提示使用者可以刪除，大約可以釋放 4.2 GB。
- R10.6 更新：app 會定期檢查新版本（設定裡也可以手動檢查），有新版時詢問使用者，同意後自動下載、驗證、替換並重新開啟。下載的檔案要驗證完整性，而且新版 app 的簽章要跟目前的 app 相符，否則拒絕安裝。錄音或轉錄進行中不能更新。更新後資料不能遺失，資料庫要自動遷移。更新檔放在哪裡由發布的人決定（Q1），app 裡可以設定更新網址。
- R10.7 app 更新後，麥克風和系統聲音權限不需要重新允許。

### R11 系統整合（P0）

- R11.1 選單列：錄音控制（開始、暫停、停止、經過時間）、目前工作的進度、打開主視窗、使用說明、結束。
- R11.2 通知：轉錄完成、會議紀錄整理好（附待確認題數）、失敗時都要通知；點通知會打開那場會議。
- R11.3 全域快捷鍵：在其他 app 裡按 ⌃⌥⌘R 也能開始或停止錄音；可以在設定裡關掉。

## 6. 非功能需求

- N1 隱私：見第 4 節。
- N2 效能：以 M1 作為下限估算，以 M3 Pro 的實測為準。
  - 即時逐字稿：暫定文字在 1 秒內出現
  - 正式轉錄：至少 5 倍速
  - 整理一小時的會議：扣掉 CLI 或 API 的回應時間，app 本身的處理不超過 10 秒
  - 任何工作在進行時，介面都不能卡住
- N3 穩定：錄音不能遺失（R1.5）；任何失敗的工作都要能重試；資料庫遷移失敗時不能損毀原本的資料，所以遷移前要先備份。
- N4 系統需求：
  - Apple Silicon（M1 以上）、macOS 26 以上
  - 記憶體：8 GB 以上。app 內轉錄加說話者辨識的峰值約 2.9 GB，會議長短影響不大（3.5 起長錄音分段轉錄，4 小時的會議 2.9 GB，實測）
  - 磁碟：模型約 1.7 GB（轉錄 1.66 GB＋說話者辨識 21 MB），加上錄音（m4a 實測約每小時 10～30 MB）
- N5 介面：繁體中文；使用 macOS 原生元件；支援深色、淺色模式；常用操作都有鍵盤快捷鍵；VoiceOver 能讀出主要元件。
- N6 安全：不開任何網路連接埠；呼叫外部程式一律用參數陣列；API key 存在鑰匙圈。
- N7 可維護性：沿用 SDD 流程；DEBUG 版保留 shiyinctl 控制通道，用來做驗證。

## 11. 第 3.2 版：轉錄準確度（2026-10-16，使用者已確認）

### 為什麼

使用者希望轉錄更準確。目前只在公開語料上量過：遠距收音的中文會議字錯誤率 Breeze 29%、macOS 內建 25%，錯誤以漏字為主（搶話、「嗯」「對」這類短插話）；合成的中英夾雜會議上，專有名詞要靠詞彙表。另外發現三個可以改的地方：

- 線上會議錄的是雙聲道（麥克風、電腦聲音），但轉錄前被混成一軌，雙方講話重疊時會互相干擾
- 沒有先偵測哪裡有人說話，長時間安靜時 whisper 會憑空產生文字（現在靠事後過濾），段落開頭結尾也容易漏字
- 聽錯的同音字、專有名詞只能靠使用者手動「用詞修正」

使用者的決定（2026-10-16）：先量再改，照 SDD 開發。

### R14 轉錄準確度（P0）

- R14.1 評估工具（開發用）：給一段錄音和標準答案，算出字錯誤率（中文 CER、英文 WER）、關鍵詞辨識對幾個、說話者標對的比例；同一段錄音可以用不同設定重跑比較。每項改進都要用它比較改前改後。
- R14.2 線上會議（麥克風＋電腦聲音）的兩個聲道分開轉錄，再依時間合併成一份逐字稿。用喇叭開會時麥克風會收到對方的聲音，這些回音不能變成重複的段落。說話者辨識也分聲道做。
- R14.3 轉錄前先偵測有人說話的片段，安靜的部分不送去辨識。（2026-10-16 評估：漏字大增，不採用，見 tasks T-I1）
- R14.4 逐字稿校正（可以在設定裡關掉；2026-10-16 評估後預設開啟）：轉錄完，整理工具依詞彙表、參加者和上下文，找出疑似聽錯的字，列成建議；使用者可以逐條或全部接受，接受後也能還原。不會自動改掉原文。
- R14.5 詞彙表建議：從參加者名單、說話者名字、會議標題、用詞修正過的字，建議加進詞彙表；使用者確認才加入。
- R14.6 採用的改進都有設定可以關掉。關掉時，轉錄的結果跟 3.1 一樣。

### 不做

- 自己訓練或微調辨識模型
- 兩個辨識引擎的結果合併
- 即時逐字稿的準確度（系統的即時辨識不吃詞彙表，沒有可以調的地方）
- 一個段落裡換人說話時切開段落（之後再考慮）

### 驗收

- 只有確實改善、或沒有變差而且有其他好處（例如比較快）的改進，才預設開啟

- R19.2 AI 猜說話者：正式整理完後，整理工具從對話內容（互相稱呼、自我介紹、參加者名單、認識的人）猜出還沒有名字的說話者是誰，附上根據（哪一段、什麼時間），列成建議。使用者按「套用」才改名，也可以忽略。不能拖慢會議紀錄完成的時間。
- R19.3 聲紋：使用者替說話者取名（自己改或套用建議）時，拾音記住這個人的聲紋（只存在本機）。之後的會議分出說話者後，跟記住的聲紋比對，夠像的自動帶入名字並標「自動」；使用者可以改正或取消，改正後也記住。同一個人可以有多份聲紋（不同收音環境）。設定裡可以查看認識的人、改名、刪除某人或全部聲紋、關閉這個功能。聲紋不放進匯出的封包。自動帶入的名字寧可少、不能錯：誤認成別人的比例要很低（驗收標準見 tasks）。
- R19.4 偵測會議、提醒錄音：線上會議的 app（Zoom、Teams、Webex、FaceTime、Slack、LINE、Discord，以及可能在開 Google Meet 的瀏覽器）開始用麥克風、拾音沒在錄音時，提醒「要開始錄音嗎？」，一鍵開始（用設定的錄音來源）。那個 app 停止用麥克風、拾音還在錄時，提醒「會議好像結束了，要停止錄音嗎？」。只提醒，不自動開始或停止。設定裡可以關閉，也可以對某個 app 選「不要再提醒」。
- R19.5 標記重點的全域快捷鍵：錄音中，在任何 app 按 ⌃⌥⌘B 就標記重點，不用切回拾音，要有聲音或選單列圖示的回饋。設定裡可以關閉（跟錄音的快捷鍵分開）。不在錄音時不佔用這組按鍵。
- R19.6 對會議提問：在一場會議裡用自然語言提問，回答附上錄音時間點，點了跳過去。也可以對所有會議（或目前的資料夾、最近 30 天）提問，回答附上是哪一場會議、哪個時間點，點了打開那場會議並跳過去。問答紀錄保留在會議裡（跨會議的保留在提問視窗）。用設定的整理工具，可以取消；選「不整理」時不能用，並說明原因。
- R19.7 回報問題：「說明」選單有「回報問題…」。先顯示會附上的資訊：版本、macOS、晶片、記憶體、轉錄引擎、說話者辨識開關、整理工具的種類、最近失敗的工作的錯誤種類。使用者確認後，用瀏覽器打開 GitHub 的新 issue 頁面並帶入內容；也可以複製內容自己寄。不帶會議內容、檔名、API key。

## 17. 重新辨識說話者（2026-10-20，使用者已確認）

### 為什麼

使用者匯入一場麻將比賽的錄音（iPhone 語音備忘錄、52 分鐘、四個人以上），說話者辨識只分出 2 個人。實測同一段錄音：預設門檻（0.6）2 人、0.5 也是 2 人、0.45 和 0.4 是 3 人；給「至少 4 人」時分出 4 人，四人說話秒數 433／364／304／289，分得很平均。手機遠距收音、背景一直有洗牌聲，每個人的聲音特徵很接近，自動判斷時會被併在一起。一般會議（AMI 9 場）用預設值都分對，所以不改預設值，改成讓使用者告訴拾音大約幾個人。

### R22 重新辨識說話者（P0）

- R22.1 會議頁「更多」選單有「重新辨識說話者…」：可以選「大約幾個人」（自動判斷、2～12 人），按「開始」只重新分辨誰在說話，不重新轉錄。逐字稿的文字、校正、編輯、重點、會議紀錄都不變。52 分鐘的錄音要在 2 分鐘內完成。

- R22.3 這場會議記住選的人數，之後「重新轉錄」也用同一個人數。
- R22.4 沒有錄音、還在轉錄或整理、分聲道轉錄的會議不能用，按下時說明原因。

### 不做（這一版）

- 錄音前、匯入時先填人數（之後看使用情況再說）
- 重新辨識後自動重新整理會議紀錄（會議紀錄可能被使用者改過，讓使用者決定）

## 18. 第 3.6 版：說話者分錯了很好改（2026-10-20，使用者已確認規劃）

### 為什麼

3.5.1 的「重新辨識說話者」能把人數補回來，但吵雜、遠距收音的錄音，句子還是會分錯（麻將錄音用兩種方法分 6 群，一致度只有 0.53）。模型不會完美，所以要讓使用者容易改，並且在可能分不準時主動提醒；使用者不會知道有「重新辨識說話者」，也不會懷疑模型分錯。

### R23 說話者的修正（P0）

- R23.1 合併說話者：說話者的改名小視窗有「合併到…」，選另一位說話者，這位的段落全部併過去。會議紀錄裡的名字跟著換（留一個版本），兩人的聲紋合成一份。可以從「更多 → 復原說話者的調整」復原。
- R23.2 改這句的說話者：逐字稿按右鍵有「這句是誰說的」「這段連續的話是誰說的」（同一位說話者連續的幾句），選一位說話者或「新的說話者」。改過的句子之後「重新辨識說話者」時保留（跟著原本那位說話者對應到的新說話者）。可以復原。沒有段落的說話者自動拿掉。
- R23.3 分不準時提醒：說話者辨識完自我檢查，可能把人併在一起時（門檻用評估資料定），逐字稿分頁上方提示「說話者可能分得不夠…」，附「重新辨識說話者…」和「不用了」。使用者已經選過人數的會議不提示。一般會議（AMI、AISHELL-4、使用者的真實會議）不能誤報。

### 不做（這一版）

- 改過句子的說話者後重新算聲紋（要再跑一次聲紋模型，之後再說）
- 跨會議合併說話者、多層復原（只復原最近一次）

### 驗收

- 介面在真的畫面上用 AX 按過；`l10n.py check` 沒有問題；中文提示詞、匯出格式不變

## 22. Windows 版（2026-10-20，使用者已確認方向）

### 為什麼

使用者要讓用 Windows 的人也能用拾音。Mac 版的介面（SwiftUI、AppKit）、錄音（Core Audio process tap）、即時辨識（SpeechAnalyzer）、說話者辨識（FluidAudio，CoreML）、鑰匙圈、DMG 和更新都是 Apple 專屬的，Windows 上沒有，要另外寫一份。

使用者的決定（2026-10-20）：

- 用 C# .NET＋WinUI 3 寫，Mac 版不動。兩邊不共用程式碼，共用規格、提示詞、資料格式、模型、翻譯表（design-windows.md）
- 開發和驗證在這台 Mac 上的 Windows 11 ARM 虛擬機；虛擬機測不到的（x64 的顯卡、真的筆電麥克風、真的線上會議）由使用者在 Windows 電腦上試
- 第一版就對齊 Mac 3.6.0 的全部功能

### R26 範圍（P0）

- R26.1 Windows 版第一版應具備 Mac 3.6.0 的全部功能：第 5～20 節的需求照樣適用，只有 R27 列出的地方改成 Windows 的做法。R10.5（從第二版升級）不適用。
- R26.2 支援 Windows 11 的 x64 和 ARM64。
- R26.3 介面用 Windows 原生元件（WinUI 3），跟著 Windows 的淺色、深色模式；常用操作都有鍵盤快捷鍵（Mac 的 ⌘ 換成 Ctrl）；朗讀程式能讀出主要元件。
- R26.4 介面語言預設跟著 Windows 的顯示語言：繁體中文（台灣、香港）顯示中文，其他語言顯示英文（同 R12.1）。Windows 不能替一般的桌面 app 個別設定語言，所以拾音的設定裡可以另外選。介面文字跟 Mac 版用同樣的說法，只有 Windows 的名詞不同（Finder → 檔案總管、選單列 → 系統匣、⌘ → Ctrl）。
- R26.5 Mac 版的行為不能因為 Windows 版而改變；為了比對兩邊而加的程式只能在 DEBUG 版。

### R28 跟 Mac 版一致（P0）

- R28.1 中文、英文、日文的提示詞（整理、修訂、草稿、逐字稿校正、詞彙建議、猜說話者、提問、問所有會議）、JSON schema、內建範本、whisper 的提示詞，跟 Mac 3.6.0 逐字相同：用 Mac 的 DEBUG 版產生標準答案，Windows 的自動測試逐字比對。
- R28.2 匯出的 Markdown、txt、srt、vtt 跟 Mac 逐字相同；docx、PDF 的內容和結構相同（字型、版面可以不同）。
- R28.3 .shiyin 封包兩邊都能匯入對方匯出的檔案，錄音、逐字稿、說話者名字、會議紀錄、筆記、重點標記、資料夾都在。
- R28.4 正式轉錄用同一個模型檔（同一份網址和 SHA-256）、同樣的分段、接縫、過濾、低信心規則。同一段錄音，Windows 和 Mac 的錯字率差不超過 1 個百分點（評估資料：AISHELL-4、AMI、國會聽證、FLEURS 日文）。
- R28.5 資料庫結構跟 Mac 3.6.0 相同（migration v1～v9）。
- R28.6 說話者辨識的模型跟 Mac 不同，聲紋不能在兩邊之間共用。分人的準確度不能明顯比 Mac 差：AMI 9 場分出的人數、聲紋自動帶入的正確率跟 Mac 比（標準見 tasks）。

### 不做（這一版）

- Windows 10（Windows 10 已經停止支援；錄電腦聲音排除自己需要 Windows 11 的功能）、32 位元
- Microsoft Store、付費的程式碼簽章憑證（SmartScreen 第一次會擋，安裝說明教怎麼放行）。免費的開源簽章（SignPath Foundation）要用使用者的名義申請，申請下來前的版本沒有簽章

- Mac 和 Windows 之間同步會議、聲紋、設定（用 .shiyin 封包搬）
- 兩邊共用一份程式碼

| R28.6 說話者辨識 | 🟡 | AMI 混音 4 人 94.9%、AISHELL-4 6 人 96.6%，聲紋 17 位帶入 16、帶錯 0、陌生人 0；使用者的麻將錄音要使用者同意才能用 |

## 24. 待確認可以按是或否、聲紋沒把握時先問（2026-10-22，使用者已確認）

第 22、23 節是 Windows 版、iPhone 版（在各自的分支上）；這一節三個平台一起做。

### 為什麼

使用者在 iPhone 上試用的回饋：待確認的題目很多是「X 是 Y 嗎？」這種是非題，答「對」也要打字。希望是非題直接給「是」「不是」的按鈕，不確定的再打字。

### R32 待確認的是非題（P1）

- R32.1 整理時，整理工具要標出能用「是」或「不是」回答的題目，題目寫成是非題（例如「負責人是小田切嗎？」）。要使用者說出答案的題目（例如「這個系統的正確名稱是什麼？」）不算。
- R32.2 是非題顯示「是」「不是」兩個按鈕，按了就算回答。按「不是」時出現輸入框，可以填正確的答案，也可以不填。其他題目跟以前一樣用輸入框；「略過」照舊。
- R32.3 送出後跟以前一樣由整理工具依回答修正（R6.5）。回答的文字依會議語言：「是」「不是」（英文 Yes、No，日文 はい、いいえ），不是而且有填答案時接在後面。
- R32.4 Mac、Windows、iPhone 一致：同一份結構化輸出、提示詞和畫面規則，標準答案（R28、R31）要跟著重新產生。以前整理的會議紀錄沒有這個標記，一律當成要打字的題目；重新整理後才有按鈕。

### R33 聲紋沒把握時先問，認錯了一步改對（P1）

使用者的回饋：聲紋有時候帶錯人，改起來要先按「不是他」、再到逐字稿改名，只做第一步拾音學不到對的人；錯的名字還會一路帶進會議紀錄（待辦的負責人）。使用者實際的資料裡，不同的人相似度可以到 0.77（AMI 語料最高 0.42），原本的門檻 0.65 太寬。

- R33.1 聲紋很像、而且跟第二像的人差得夠遠，才直接帶入名字（標「自動」，同 R19.3）。夠像但沒那麼有把握的，不帶入，改成待確認的是非題：「『說話者 3』是 weiwei 嗎？」，附上原因（聲音跟之前的 weiwei 很像）。門檻在 design §21.4。
- R33.2 待確認裡的說話者題目（聲紋沒把握的、AI 從對話內容猜到的，R19.2）：按「是」就帶入名字並記住聲音；按「不是」可以從最像的幾位認識的人裡選，或打名字，也可以不填（就不帶入）；「略過」照舊。送出時跟其他題目一起處理，這一部分不經過整理工具。
- R33.3 會議清單和分頁上的「待確認 N 題」包含說話者題目。
- R33.4 點「自動」帶入的名字：除了「不是他」，直接列出最像的幾位認識的人和「其他人…」，選了就一次改名、記住聲音、改掉會議紀錄裡的名字。

### 不做（這一版）

- 選擇題（列出幾個選項讓使用者選）
- 記住「不是他」（存反例，下次不再帶成同一個人）、聲紋的每一份樣本看得到也刪得掉：先看 R33 之後誤認還多不多
- app 自己從題目的文字判斷是不是是非題（D90）

### 驗收

- 假伺服器回傳有標、沒標的待確認：畫面上分別是按鈕、輸入框；按「是」、按「不是」不填、按「不是」填答案各送出一次，依回答修正的請求裡是對應的文字
- 用真的整理工具整理一場會議：是非題有標出來，題目寫成是非題
- 聲紋：AMI 語料和使用者的資料庫模擬新的門檻，帶錯 0；中間的變成待確認的說話者題目，按「是」「不是」（選別人、打名字、不填）、略過各送出一次，名字、聲紋、會議紀錄的結果對；點「自動」的名字選別人，一步改好
- 按了「不是」、填到一半換分頁再回來，選擇和答案都還在（R20.6 的草稿）
- 標準答案重新產生後，Windows 的測試、iPhone 模擬器的比對都通過；英文介面、日文會議各看一次

## 25. 很短的一句被算到旁邊的人（2026-10-22，使用者回饋）

### 為什麼

使用者匯入一段兩個人的訪談（輪流講話），逐字稿裡蔡康永說的「就只有這件事而已」（約 1 秒）接在阿滴的下一句前面，兩句都被標成同一位說話者。這不是聲紋認錯人（R33），是說話者辨識沒把很短的一段當成換人：短的一段被併進旁邊那個人。訪談、聊天、會議裡一來一往的短句（「好」「對啊」「就只有這件事而已」）常常遇到，使用者要一句一句用「這句是誰說的」（R23.2）改。

### R34 短句的說話者（P1）

- R34.1 輪流講話時，很短的一句（約 2 秒以內）要盡量標成真正說話的人，不能因為太短就併進旁邊那個人。用有標準答案的評估資料量（AMI、AISHELL-4，只算沒跟別人同時講話的句子）：2 秒以內的句子標對的比例要明顯提高，整體（含長句）不能變差，分出的人數不變，處理時間不明顯變長（design §6.3.2）。
- R34.2 同時有兩個人講話（一個人講、另一個人插一句「嗯」）時，拾音一次只標一個人，這一版不處理。
- R34.3 Mac、iPhone 用同一份說話者辨識（FluidAudio），一起改；Windows 的說話者辨識不同（D58），用 Windows 的評估資料另外量、另外改（design-windows §9）。
- R34.4 只影響之後轉錄、重新轉錄、重新辨識說話者的會議；以前的會議不動，要的話用「重新辨識說話者」（R22）。

### 驗收

- 評估資料的數字照 R34.1（寫進 design §6.3.2）
- 使用者那段訪談重新辨識說話者後，「就只有這件事而已」那一句標成蔡康永（要使用者確認，或使用者同意後用那段錄音的複本跑）

### 驗收結果（2026-10-22，Mac）

| 項目 | 結果 | 說明 |
|---|---|---|
| R34.1 評估資料 | ✅ | 沒重疊的 2 秒內的句子標對：AMI 9 場 24.3% → 59.8%、AISHELL-4 91.3% → 95.7%；日文合成會議 90% → 100%；分出的人數、聲紋比對、分不準的提醒不變（design §6.3.2）。完整的轉錄流程（Breeze）：說話者標對（按時間）AMI 94.6% → 96.1%、AISHELL-4 96.7% → 97.2%，文字相同，時間多約 5% |
| R34 使用者的訪談 | ✅ | 「就只有這件事而已」從阿滴改成蔡康永；404 段改了 7 段 |

## 26. 沒有 claude、codex 的電腦（2026-10-22，使用者回饋）

使用者回饋：Windows 上沒有 claude CLI 或 codex CLI 時，整理工具預設還是 claude CLI，每場會議都「整理失敗」，訊息叫人「安裝指令」，一般使用者完全不知道怎麼辦。Mac 也一樣（只是 Mac 的使用者比較常已經裝了 Claude Code）。使用者決定：沒有 CLI 時先不整理、提示去設定，Mac、Windows 一起改。

### R35 還沒設定整理工具（P1）

- R35.1 使用者還沒選過整理工具時，自動用這台電腦上有的 CLI（先找 claude，再找 codex）；兩個都沒有就先不整理：錄音、轉錄照常，不排整理、校正、猜說話者，不會出現「整理失敗」。之後裝了 CLI 就自動用上。使用者選過的整理工具（包括「不整理」）照舊。
- R35.2 「還沒設定」跟使用者選的「不整理」分開說：會議頁原本放會議紀錄的地方顯示「還沒設定整理工具」和打開設定的按鈕；要用到整理工具的動作（整理、依回答修正、提問）被擋下時也這樣說。
- R35.3 首次使用引導、設定的整理工具：找不到 CLI 時預設「之後再設定」，CLI 的選項寫明是給已經在用 Claude Code、Codex 的人；填 API key 的選項（Anthropic、OpenAI、Gemini）附「取得 API key」的連結。
- R35.4 選了 claude 或 codex、這台電腦卻找不到時，錯誤訊息說明怎麼辦：沒有在用 Claude Code（Codex）的話，到設定改用 API（填 API key）或「不整理」。
- R35.5 Mac、Windows 一起改；iPhone 沒有 CLI，接 Mac 的程式時照 R35.2、R35.3 調整。

### 驗收

- 沒有 CLI、沒選過整理工具：引導預設「之後再設定」；匯入一場會議，轉錄完成、沒有排整理、沒有失敗的通知，會議頁顯示「還沒設定整理工具」和按鈕（Mac 的 DEBUG 版、Windows 的虛擬機，在真的畫面上按過）
- 有 claude、沒選過：照舊用 claude
- 選了 claude 但找不到：錯誤訊息是 R35.4 的說法
